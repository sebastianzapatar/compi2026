El Evaluador (Tree-Walking Interpreter)

Dándole vida al Árbol Sintáctico

1. Teoría: ¿Qué es un Evaluador?

El Evaluador es el corazón del intérprete. Es el componente que toma la estructura generada por el Parser (el AST) y realiza las acciones reales: suma números, asigna variables, y corre bucles.

Tree-Walking Interpreter: Es un diseño donde el intérprete ejecuta el programa viajando ("caminando") recursivamente por los nodos del Árbol Sintáctico Abstracto (AST) de arriba hacia abajo.

1.1 Motivación: ¿Para qué sirve?

¿Por qué molestarnos en escribir un Evaluador desde cero?

  • Entender la "Magia": Desmitificar cómo lenguajes como Python o JavaScript ejecutan tu código por debajo.
  • Domain Specific Languages (DSLs): Crear lenguajes pequeños a medida para reglas de negocio (ej. calculadoras de impuestos, motores de automatización).
  • Herramientas: Los mismos principios se usan para construir linters, formateadores o motores de refactorización.

2. El Flujo de Vida del Código

Así encaja el Evaluador en nuestro sistema:

  • 1. Lexer: Convierte texto a Tokens.
  • 2. Parser: Convierte Tokens a AST (Árbol).
  • 3. Evaluador: Recorre el AST y evalúa operaciones para producir Objetos en Memoria (Resultados).

3.1 ¿Por qué es lento el Tree-Walking?

  • Muchos saltos de memoria (cache misses): Los nodos del AST son objetos esparcidos por toda la memoria RAM (Heap). El CPU no puede predecir qué leer después.
  • Recursión constante: Cada operación requiere múltiples llamadas a la función evaluate(), llenando el Call Stack y agregando overhead de ejecución.
  • No hay optimización: No aplicamos inlining ni compilación JIT (Just In Time). En un bucle while, re-analizamos el árbol desde cero en cada ciclo.

3.2 Lenguajes y sus Modelos

  • Tree-Walking: Ruby (versiones muy antiguas), lenguajes educativos, prototipos iniciales, motores de reglas sencillos.
  • Bytecode VM: Python (CPython), Java (JVM), C# (CLR). Logran un excelente equilibrio entre portabilidad y velocidad.
  • Compilados Nativos: C, C++, Rust, Go. Velocidad máxima absoluta, pero fuertemente dependientes de la arquitectura del procesador (no portables directamente).

4. ¿Por qué usamos Tree-Walking?

Ventajas

  • Sencillez: Es el puente más lógico entre la estructura del código y su ejecución.
  • Desarrollo Rápido: Ideal para lenguajes educativos, DSLs (Domain Specific Languages) y prototipos.
  • Código Limpio: Mapeo directo 1 a 1 entre nodos del AST y funciones de Python.

Desventajas

  • Lentitud: Seguir punteros de árbol arruina la memoria caché del CPU.
  • Loops Ineficientes: En un while, un tree-walker debe re-analizar y recorrer los mismos nodos del árbol miles de veces.

Para aprender cómo se estructuran las reglas semánticas de un lenguaje, no hay mejor enfoque que Tree-Walking.

7. La Memoria: environment.py

El Environment es una tabla Hash (Diccionario) que asocia nombres de variables (Identificadores) con sus Valores (Objects).

class Environment:
    def __init__(self, outer = None):
        self._store: Dict[str, Object] = {}
        self._outer = outer # Puntero al scope padre

    def get(self, name: str) -> Optional[Object]:
        value = self._store.get(name)
        # Lexical Scoping: Si no está aquí, busca afuera
        if value is None and self._outer is not None:
            value = self._outer.get(name)
        return value

    def set(self, name: str, value: Object):
        self._store[name] = value
        return value

7.1 Lexical Scoping y Closures

El atributo self._outer es la magia detrás de los Closures.

Cuando defines una función, ésta guarda el "Environment" en el que nació.

Al ejecutarla, crea un nuevo environment (inner) que apunta al guardado. Así, las funciones pueden "recordar" variables declaradas afuera.

8. El Evaluador (evaluator.py)

La función evaluate(node, env) es una función gigantesca de despacho recursivo.

def evaluate(node: ast.Node, env: Environment) -> Object:
    # ── Sentencias ──
    if isinstance(node, ast.LetStatement):
        return _eval_let_statement(node, env)
    
    # ── Expresiones compuestas ──
    if isinstance(node, ast.InfixExpression):
        left = evaluate(node.left, env)
        if _is_error(left): return left
        right = evaluate(node.right, env)
        if _is_error(right): return right
        return _eval_infix_expression(node.operator, left, right)
    ...

Nota cómo evalúa el lado izquierdo, luego el derecho, y luego opera. ¡Así de simple es un Tree-Walker!

8.2 El concepto de "Truthiness"

¿Qué significa if (5) { ... }?

Hemos programado las reglas estrictas de qué es falso y qué es verdadero (Truthiness) en _is_truthy():

  • Falsy: false, null, 0, 0.0, ""
  • Truthy: Cualquier otro valor (true, 5, "hola")
def _is_truthy(obj: Object) -> bool:
    if obj is NULL or obj is FALSE: return False
    if isinstance(obj, Integer): return obj.value != 0
    if isinstance(obj, String): return len(obj.value) > 0
    return True

9. Propagando Return y Errors

Dado que la evaluación viaja profundamente por la recursión, ¿cómo hace un return o un Error para detener la ejecución inmediatamente?

R: Usamos objetos Wrapper especiales. Cada función verifica si el resultado evaluado es un ReturnValue o un Error. Si lo es, aborta su propia evaluación y retorna ese objeto hacia arriba (burbujeo).

10. Ejecutando Bucles (For / While)

Un bucle sencillamente ejecuta evaluate(node.body, env) repetidamente bajo un ciclo nativo de Python.

def _eval_while_statement(node, env):
    result = NULL
    while True:
        condition = evaluate(node.condition, env)
        if not _is_truthy(condition): break # Salir si condición es falsy

        result = evaluate(node.body, env)
        
        # Soportamos break y continue interceptando las señales
        if isinstance(result, BreakSignal): return NULL
        if isinstance(result, ContinueSignal): continue
        if isinstance(result, (ReturnValue, Error)): return result
    return result

11. Errores Comunes al Crear un Evaluador

Si intentas crear tu propio evaluador, ten cuidado con estos "gotchas":

  • Fugas de Scopes: Olvidar crear un Environment "inner" al invocar una función, sobrescribiendo variables globales por accidente.
  • Pérdida de Retornos: Olvidar propagar el objeto ReturnValue hacia arriba en la recursión, haciendo que el return se ignore si está dentro de un if anidado.
  • Evaluar antes de tiempo (Eager Eval): Evaluar las ramas if y else ANTES de saber si la condición es verdadera (¡Ejecutaría el código de ambas ramas!).
